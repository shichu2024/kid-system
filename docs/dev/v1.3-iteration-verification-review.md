## 2. 报告暴露但未识别的真实问题

### 2.1 R-001（高）· 安装完整性脆弱性：init 依赖技能包物理文件，缺失时静默走样

**证据链**：测试环境只分发了 9 个 SKILL.md（`.agents/skills` 布局）。init 的「复制技能包 templates/」无法执行 → AI 转而按 SKILL.md 里的文字描述**现场生成**模板、schema、references、knowledge → 生成的 journal-schema rule_id pattern 变成 `^rule-[a-z0-9-]+$`、模板枚举变成中文五值——即报告 P-001/C-002 的全部「证据」都来自这些走样产物。

**危害等级：高。** 走样 schema 意味着：若后续技能读取 vault 内自造的 `99_system/references/`，安全数据（过敏、窒息清单、就医红线）也可能走样——**安全滤网的事实依据被污染**。

**修复（WP1）**：
1. kid-init 硬约束新增：铺设模板前**实测清点技能包模板源**（`ls` 计数 8/语言）；源缺失或数量不符时输出 ⚠⚠ 阻断级告警并停止铺设，明确提示「技能包安装不完整，请重新安装完整技能包」，**禁止现场编造模板/schema/references/knowledge 替代**
2. kid-init 硬约束新增：**只铺设模板与配置**；`references/`、`knowledge/` 永不复制进 vault（技能运行时直接从技能包读取，见 §2.3）

### 2.2 R-002（高）· 多儿童方案路径规范缺失 → 测试产出路径漂移

**证据链**：DESIGN §4.4 与全部 SKILL.md 的 `applies_to` 均为 `02_plans/YYYY-MM-DD.md`（单儿童假设、三节合一）；demo-vault 也如此。但测试（28 月龄单儿童！）产出了 `02_plans/tangtang/menu-2026-09-08.md`、`learning-2026-09-08.md`、`games-…`、`plan-…` 四个文件——按儿童分目录 + 模块前缀拆分。多孩家庭下「哪个儿童的方案放在哪」**规范真空**，AI 自行发明了布局。

**危害**：kid-review 拉取 `02_plans/`、kid-menu 3 天查重窗口、Web 仪表盘 listDir 全部依赖既定路径约定，布局漂移直接破坏闭环数据流。

**修复（WP2）**：DESIGN §3/§4.4 与 SKILLS_SPEC 明确多儿童布局——推荐方案：
- 方案 A（推荐）：`02_plans/<child-id>/YYYY-MM-DD.md`（所有儿童统一带子目录，单双孩一致，不因添加二孩而迁移历史文件）
- 01_journal 同理 `01_journal/<child-id>/YYYY-MM/YYYY-MM-DD.md`
- 同步更新 9 个 SKILL.md 的 `applies_to`、kid-review/kid-menu 的读取路径约定、demo-vault 迁移、check-frontmatter.mjs 的路径分类正则、Web 仪表盘 listDir 逻辑、bench cases 的 path_glob
- 每日方案保持**三节合一单文件**（menu/learning/games 不拆分），禁止模块前缀文件名

### 2.3 R-003（中）· init 铺设范围未设禁止项 → references/knowledge 被擅自复制进 vault

**证据链**：测试 init 往 vault 的 `99_system/` 铺了 references×7 + knowledge×3（共 28 个系统文件）。SKILL.md 步骤 2 只列了模板 + config，但**未写「不得铺设知识库」**，AI 按「更完备」的善意推断执行了。后果：vault 内静态知识副本会随技能包升级**过期失真**（尤其 safety-rules 的就医红线），形成「双真相源」。

**修复（WP1 内一并处理）**：kid-init 步骤 2 增加显式禁令与理由：「references/ 与 knowledge/ 由技能运行时从技能包读取，**严禁复制进 vault**（避免升级后 vault 内副本过期失真，尤其安全红线）」；自检清单加一项「99_system 下无 references/knowledge 目录」。

## 5. 虚假问题根因复盘（写给后续测试）

本次报告 3 条候选问题中 2 条本已被其三轮复核排除，但**第 3 条（P-001）的三轮复核失败了**——它每一轮都在验证「测试 vault 内的走样文件」与「SKILL.md 声称」的矛盾，从未回到**仓库真相源**（`references/journal-schema.json`）核对。教训固化为规则：

1. **复核必须到上游**：凡声称「X 与 Y 不一致」，X 和 Y 都必须取自分发源（本仓库），不得取自运行产物
2. **先解释产物来源**：测试中出现规范里不存在的字段/枚举（如 care_mode、sleep_quality、安全等级）时，第一反应应是「运行环境安装不完整导致现场编造」，而非「设计矛盾」
3. **安装完整性先于功能测试**：全链路测试前先清点技能包文件数（skills 9 + templates 16 + references/knowledge 若干），数量不符即终止并报告环境问题
